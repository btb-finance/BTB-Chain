# Oracles: Randomness and Real-World Data, Built In

On most chains, contracts cannot get a random number or a price on their own. They rely on a separate oracle network, such as Chainlink, and pay it for every request. **On BTB Chain, oracles are a native feature of the validator set**: randomness, price feeds and web data come from the same validators that run consensus, and arrive as ordinary tables your app can query and subscribe to.

This works because BTB validators already do the three things an oracle network does:

- **Reach agreement** on values (consensus),
- **Hold shared threshold keys** (also used for [cross-chain signing](CROSS_CHAIN.md)), and
- **Run servers** that can fetch outside data (they are a decentralized cloud).

## What BTB provides

| Feature | What it replaces | How BTB does it |
| --- | --- | --- |
| Verifiable randomness | Chainlink VRF | Threshold signature over each block, produced jointly by validators |
| Price feeds | Chainlink Data Feeds | Validators fetch prices from many sources, agree on the median, write it to a system table |
| Real-time data streams | Low-latency feeds such as Chainlink Data Streams or Pyth | Feed rows update every block; apps subscribe like any Convex-style query |
| Custom web data | Chainlink Functions | Contracts request an HTTPS call; validators each fetch it and agree on the result |
| Automation | Chainlink Automation | Native `@cron` and scheduled functions |
| Data for other chains | Oracle networks on each chain | BTB signs reports with its threshold key; contracts on Ethereum, Solana and others verify them |

The two caveats that matter, stated up front:

1. **No trusted dealer, but the first key needs an honest majority of the first validators.** A chain whose genesis has no `group_key` generates epoch 0's key in its first `dkg_window` blocks; until it exists `random_bytes` traps with `RandomnessUnavailable` and blocks carry no beacon. `btb-node init-testnet --oracle true` does this. `--insecure-dealer true` (testnets only) keeps the old behaviour, where the tool deals the key and sees every share; the first epoch change already reshares it on chain, but whoever ran the tool knew the original polynomial. A mainnet genesis must not set `group_key`.
2. **The committee is by validator count, not stake.** Each validator holds one share and the threshold is `n - floor((n - 1) / 3)` (more than two thirds of the validators), whatever their stake. Stake weighting would give a validator one *virtual share* per stake unit: shares are limited to 256 (`MAX_HOLDERS`, the cost of a DKG grows with the square of the share count), a validator would have to produce and gossip one partial per virtual share for every block, and rounding stake into at most 256 shares changes weights at every epoch anyway. The beacon's security argument needs only that fewer than `t` holders are corrupt; since the validator set is itself chosen by stake and consensus tolerates less than a third of the stake, the stake-weighted guarantee is approximated by the count-based one whenever stakes are within small factors of each other. A validator with a very large stake and many small ones is the case where it is weaker. Virtual shares are future work.

## 1. Verifiable randomness

### Design

Every block height `h` has one **beacon value**, the threshold BLS signature of the committee's group key on

```
"btb.beacon.v1" || chain_id:u64be || epoch:u64be || height:u64be
```

(BLS12-381, public keys in G1, signatures in G2, `blst`, Apache-2.0). It is unique: a BLS signature is a deterministic function of key and message, so any `t` valid partial signatures combine to the same 96 bytes. Anyone can verify it against the group key stored in the genesis state. The 32-byte **seed** is `SHA256("btb.beacon.seed.v1" || signature)`.

**Release rule.** A validator releases its partial signature for height `h` only after its own replica **committed** block `h`. Consequences:

- The transactions that consume `beacon(h)` are final before any partial exists, so their content cannot depend on the randomness.
- Nobody can compute `beacon(h)` early. With fewer than `t` partials every candidate signature is equally likely: the tests show that interpolating `t - 1` partials yields a value that does not verify, that padding with invented partials is rejected, and that the output passes bit-balance and avalanche sanity checks.
- Block `h` executes only when its beacon is known. A committed block waits in a queue (`pending_exec` in the driver) until `t` partials arrive; a node that is late or catching up asks its peers (`Want{height}` answered with the finished beacon, verified before use, stored with the block history). One extra network round trip per block is the price of the rule. Consensus attestation ([CONSENSUS.md](CONSENSUS.md#randomness-beacon-and-execution-lag)) already tolerates execution lag.

**Why the committee cannot bias it.**

- *Grinding by the block producer.* The proposer of `h` fixes the payload without knowing `beacon(h)`; it cannot see the outcome and then decide what to include. It could choose between payloads only by guessing.
- *Grinding by a coalition of validators.* Fewer than `t = n - floor((n - 1)/3)` holders (in particular the `f < n/3` the protocol tolerates) cannot compute the beacon, and holders who withhold their partials can only stall it: with `n - f >= t` honest holders the beacon still appears, so a minority can delay but not steer or censor it (`liveness_with_exactly_f_offline`). Withholding for one height cannot select between two outcomes either, because there is exactly one valid value.
- *Bad partials.* Partials are checked against the holder's public share (`Collector`): optimistically, with one verification of the aggregate, and per partial only if that fails; a holder whose partial fails is ignored for that height. A message is accepted only from the peer whose consensus key is the holder named in it (`malicious_partials_are_rejected_and_do_not_block_liveness`, `forged_misattributed_and_out_of_window_partials_are_ignored`).
- *Key generation bias.* With the testnet dealer the dealer knows everything (see the caveat). With the joint-Feldman DKG below, a rushing adversary can bias the *distribution of the group public key*, which Gennaro, Jarecki, Krawczyk and Rabin showed does not weaken discrete-log signatures such as BLS; the beacon *values* are still unpredictable and unique.
- *Last-revealer effects.* The only party who learns `beacon(h)` first is whoever completes the aggregation, a moment later than every other honest validator, and the value cannot be changed by it.

Trust model: unpredictability needs fewer than `t` colluding holders of the current generation; liveness needs at least `t` honest ones; both assume the key was generated by the on-chain DKG below (or, on testnets with `--insecure-dealer`, honestly dealt).

### Key provisioning and the DKG

`btb_oracle::dkg` is the deterministic protocol library (joint-Feldman with complaints, resharing to a new committee) and `btb_chain::dkg` runs it **on the chain**: every message is a transaction (`Dkg`, tag 14), so the board is the chain's own ordered, authenticated broadcast, the whole transcript is replayable and auditable (`btb_oracleDkg`), and every node derives the same keys.

**Who generates what.** The beacon key of epoch `e` is generated by the validators of epoch `e` themselves: the committee is exactly the epoch's validator set, in consensus order, holder `i` has x-coordinate `i + 1`. The key of epoch `e` signs the beacons of the blocks of epoch `e` (state `50 30 e`).

**Schedule** (window `W = dkg_window`, `W >= 6`, `2W <= epoch_len`; epoch `e` ends at height `we = (e + 1) * epoch_len`, `ws = we - W + 1`):

| Heights | What happens |
| --- | --- |
| `ws` (begin of block) | The chain **locks** the next validator set (`staking::select_set`) into a *session* for epoch `e + 1`. Staking then uses exactly this set for epoch `e + 1` (stake changes, unbonding or jailing in the last `W` blocks count one epoch later: a validator slashed inside the window still serves the next epoch), so the beacon committee is the validator set. If the chain has the key of epoch `e` the session reshares it, otherwise it deals a fresh key. |
| `ws + 1 ..= ws + W/2` | **Deal.** Each dealer posts `Deal { target, eph, commitments, ciphertexts }`. Dealers are the new committee (fresh) or the holders of the old key (reshare). |
| until `we` | **Complain.** `Complain { target, dealer, shared, proof }`, see below. |
| end of block `we` | **Finalize.** Qualified dealers = those that dealt and were not upheld against. With at least `t` qualified (fresh) or `t_old` qualified (reshare) the group key and every public share are derived from the board and stored as the key of epoch `e + 1`. Otherwise the previous key carries over (below). Boards older than the previous generation are pruned. |
| first `W` blocks of a chain | Same, as a fresh session for epoch 0, if the genesis has no `group_key`. |

**Deal.** A dealer's polynomial `f_i` has degree `t - 1` with `t = n - floor((n - 1)/3)` for the new committee of `n`. The deal carries the Feldman commitments `C_{i,k} = a_{i,k} * g1` (G1, 48 bytes each) and, for each recipient `j`, the share `f_i(j + 1)` encrypted to `j`'s consensus key. In a reshare the dealer's constant term is its old secret share, and the chain checks at the door that `C_{i,0}` equals the dealer's published old public share (a dealer cannot reshare a different secret). The chain also checks the shape, that the commitments are valid subgroup points, that the sender's key is a dealer's, and that it did not deal already.

**Encrypted shares.** The recipient's Ed25519 consensus key is also its delivery key (no extra registration): the dealer picks an ephemeral key `E = e*B` and encrypts the share with ChaCha20-Poly1305 under `SHA256("btb.dkg.key.v1" || e*A_j || chain, epoch, dealer, recipient)`; the same context is the associated data, so a ciphertext cannot be moved to another slot. This uses `curve25519-dalek` and `chacha20poly1305` (both permissive). We use Edwards-curve ECDH instead of `x25519-dalek` because a complaint needs a proof about the Diffie-Hellman value, and that proof works on points, not on the u-coordinates X25519 exposes. Signing and Diffie-Hellman with one key is acceptable here because the DH value is only ever hashed with the context and never used as a signature nonce.

**Complaint, decided by the chain.** A recipient that finds a share missing, undecryptable or inconsistent with the commitments (`s * g1 != sum_k C_k (j + 1)^k`) posts the shared point `S = a_j * E` with a Chaum-Pedersen (DLEQ) proof that `log_B(A_j) = log_E(S)`. The chain verifies the proof, decrypts that very ciphertext, checks the share against the commitments, and:

- bad share (or garbage) -> the **complaint is upheld**, the dealer is disqualified at once;
- good share -> the complaint reverts (`ComplaintRejected`); the accuser pays the fee, the dealer stays qualified.

So no justification round is needed (an honest dealer cannot be disqualified: the proof ties `S` to the accuser's key, and the share it opens is the one the dealer published). The reveal makes one share of one accuser public; an accuser that already got a bad share loses nothing, a false accuser only exposes a share the dealer knows. An accuser without a valid proof (wrong key, damaged proof) is refused (`BadProof`). A recipient whose key is not a valid point gets no usable ciphertext and cannot complain; it simply gets no share and does not sign.

**Silent dealers** never post a deal and so are not qualified; they cost nothing more than their missing contribution. Complaints against a dealer that never dealt are refused (`NoSuchDeal`).

**Key and shares.** With qualified set `Q`, the group key is `sum_{i in Q} C_{i,0}` (fresh) or `sum_{i in Q'} lambda_i C_{i,0}` over the `t_old` lowest qualified old holders `Q'` with Lagrange coefficients `lambda_i` at 0 (reshare), so the **group public key does not change across epochs**: old beacons keep verifying, contracts and other chains see one key forever. Validator `j`'s share is the same combination of the shares it received, checked against the public share on the board. The Lagrange combination of the dealers' commitments is computed coefficient by coefficient, so deriving all `n` public shares costs `t` full multiplications per dealer, not `n * t`.

**Failure and liveness.** If fewer than the needed number of dealers qualify (too many silent or cheating dealers), the epoch **keeps the previous key and its holders** unchanged (`50 30 e+1` is a copy), the session is marked `failed`, and the chain goes on; the next epoch tries again from that key. Consequences, stated plainly:

- A failed *genesis* DKG leaves epoch 0 with no beacon at all; blocks keep running without randomness; the next epoch's session deals a fresh key (there is nothing to reshare).
- **Losing the beacon committee (degraded mode).** A carried-over key is only as live as its holders. The decision whether to carry it over is made from chain state at the end of the DKG window, never by a timeout or a vote. Let `K` be the old key (threshold `t`) and `r` the number of its holders that are validators of the new epoch (the set locked at the start of the window).
  - `r >= t`: the key carries over, as before. Its signers are validators, and the chain already needs more than two thirds of them online to finalize anything.
  - `r < t`: a beacon would need `t - r` signatures from validators that have left, and nothing the chain can check binds them. The chain does not wait for them. The new epoch gets **no key** and the chain enters **degraded mode** (record `50 34`): blocks execute without a beacon, `random_bytes` traps with `RandomnessUnavailable` (the same state as the genesis DKG window), and everything else, including reports for other chains, which pause because no key can sign them, is unaffected. At the first block of the new epoch a **fresh** key generation (not a reshare) opens among its validators with the usual window. When it succeeds the new key signs from then on, the degraded record is deleted and a key change is stored under `50 32 epoch` (old and new group key, the block where degraded mode began, the block where it ended). If it fails, the next epoch tail retries with a fresh generation, and degraded mode lasts until one succeeds. No balance changes anywhere in this path, so the supply is untouched.
  - *Key change.* The group key changes, so anything that pins it must follow. Read `btb_oracleKeyChanges` (and `degraded` in `btb_oracleConfig`). A verifier of beacons or reports for another chain must treat a report signed under the new key as valid only after it has seen the key change of this chain (on-chain data, the same state a light client already follows); reports queued before degraded mode and not yet signed are not signed after it.
  - *Departed holders.* Holders that leave the set are expected to keep their node running and signing until the next successful reshare: their stake sits in unbonding (`unbonding_blocks`, long) and stays slashable by the normal evidence rules. The chain does not count on this, which is why degraded mode exists: if they do, the reshare, which needs them as dealers, is far more likely to succeed in the first place.
  - *Determinism.* `r`, `t`, the failed session and the epoch are all in state at block `we`; every node takes the same branch at the same block. Nodes need no timer and no extra message; the existing wait for a beacon is unchanged (an epoch without a key needs none).
  - *No bias from a minority.* Degraded mode can only be entered when the reshare failed, which needs fewer than `t_old` of the old holders to deal: a coalition of fewer than a third of the validators cannot cause that alone (the dealers are all the old holders), and it also needs the leavers. In degraded mode the beacon is *absent*, not replaced, so there is nothing to bias; the fresh key is generated by the joint-Feldman protocol among the current validators, whose group key a minority of them cannot choose or learn. A coalition that holds the leavers can at most keep the old key from being reshared, and doing so loses them their share of the old key at the key change. A caveat that stays: while a chain is in degraded mode, contracts that need randomness fail, so a minority that can force the failed reshare can deny randomness for up to one DKG window plus one epoch.
- Only the old holders deal in a resharing, but every new committee member receives its share before the epoch starts (the key is finalized in the epoch's last block), so a validator that joins at an epoch boundary signs beacons from its first block.

**After the handover.** Resharing does not make old shares mathematically useless (they stay valid shares of the same group key). The protection is that (a) the chain accepts partials only from the *current* key's holders, which no longer include a validator that left, (b) shares of one generation and another do not combine (a mix of `t - 1` old and some new shares interpolates to garbage: `resharing_keeps_the_group_key_through_three_epochs_with_a_validator_set_change`), and (c) nodes **erase** the shares of generations older than the key now in use. An attacker must therefore corrupt `t` holders *of one generation* within the window in which that generation's share still exists, not accumulate shares over the lifetime of the chain (proactive security).

**Node behaviour.** `btb-node` runs the agent after every executed block (`btb_chain::dkg_agent`): it deals when a session opens, checks every share addressed to it and complains about bad ones, and derives its share when the session is done. The polynomial and the ephemeral key are derived from the consensus secret, chain id and epoch, so a restart re-sends the same deal. Transactions are signed by the consensus key, whose account pays the fee (`60,000 + 1,500 * (t + n)` gas per deal, `250,000` per complaint), so **the consensus key's account needs a little BTB** (the testnet tool uses one key for both). Shares are kept in `<dkg_dir>/share-<origin>.json` with mode `0600`, optionally encrypted with the passphrase in `BTB_KEY_PASSPHRASE`; the file is only a cache: a node that lost it re-derives the share from the board while the board still holds that generation (two epochs), using its consensus key. A node that is replaying old blocks sends nothing.

**Cost.** A deal is about `(t + n) * 48` bytes; for 100 validators about 8 KB per dealer and 800 KB of board per epoch. Finalizing an epoch for 100 validators does about `t_old * t` G1 multiplications (a second or so) once per epoch. Tests: `crates/btb-chain/tests/dkg.rs` (honest genesis, bad share to one member, false complaint, silent dealer, fewer than `t` qualified at genesis and in a reshare, carry-over and recovery, reshare through three epochs with a validator joining and one leaving, handover property, every refusal), `crates/btb-oracle/src/dkg_crypto.rs` (delivery and proofs), `crates/btb-node/tests/oracle_cluster.rs` (a real cluster: genesis DKG, an epoch change with a validator leaving, a restart, beacons verified under one key across epochs).

**Remaining trust.** Joint-Feldman lets a rushing adversary bias the *distribution* of the group public key, which does not weaken BLS (GJKR); a corrupt majority of any one committee (`>= t` of that generation) can sign anything for as long as it holds those shares. `--insecure-dealer` is the only mode in which one party knows the key; it exists for local testnets.

### Using it

```rust
#[btb::mutation(randomness)]
pub fn roll_dice() -> u64 {
    let n = random::range(1, 7); // 1..=6, unbiased, from the beacon
    // ...
    n
}
```

- `random::bytes(n)` (at most 1024), `random::u64()`, `random::range(lo, hi)` (rejection sampling, no modulo bias). They call the host call `random_bytes` ([LANGUAGE.md](LANGUAGE.md#host-calls)).
- **Per-call derivation.** `tx_seed = SHA256("btb.rand.tx.v1" || beacon_seed || tx_id)`; the `c`-th call of the transaction gets `SHA256("btb.rand.out.v1" || tx_seed || c:u64be || j:u32be)` blocks. A cron run uses its receipt id as `tx_id`. Replicas derive identical bytes (`randomness_is_deterministic_across_replicas_and_depends_on_the_beacon`), two transactions or two calls never share bytes.

**Safety rules built into the runtime.**

- **Marker, enforced at run time.** `#[btb::mutation(randomness)]` and `#[btb::cron(randomness, every = "N blocks")]` export the symbol `btb_randomness_<kind>_<name>`. The VM reads it from the ELF on every call (it is not in the manifest and the caller cannot change it). A `random_bytes` call from a query, an action or an unmarked function traps with `RandomnessForbidden` (a read-only host is refused even if flagged). A marker on a query or action, or without a matching entry point, makes the contract invalid at deploy. The macro rejects `#[btb::query(randomness)]` at compile time.
- **Never callable by other contracts.** There are no cross-contract calls; if they are added the callee must run with the flag off. A marked function is reached only by a transaction or a scheduled cron.
- **No retry-until-you-win.** A function that is marked `randomness` is always charged its **full gas limit**, whether it succeeds, aborts or traps, so aborting after a bad draw is never cheaper than keeping it, and a caller cannot make bad outcomes fail by running out of gas (`randomness_costs_the_full_gas_limit_even_when_the_call_fails`). Pick a tight gas limit.
- **Queries can't use it.** The seed is only ever read by marked mutations and crons, which go through consensus.
- **A chain without a beacon** (no oracle config in the genesis, or the first `dkg_window` blocks of a chain that generates its key on chain) traps marked calls with `RandomnessUnavailable`; the seed record is deleted in beaconless blocks so a stale seed can never be read. `btb dev` has no beacon and serves marked functions from a fixed, public seed so they can be tried out; that output is not random.
- **Gas.** `random_bytes` costs `300 + 2 * len` gas, charged before the call.

## 2. Price feeds and real-time data

### Built

1. A feed is a pair in the genesis oracle config: `{id, name, decimals}` (for example `0`, `BTC/USD`, `8`), up to 64, plus `max_age_blocks` (default 100).
2. Each validator periodically observes every pair (from [its exchange sources](#sources-on-the-validator-built)) and signs `(pair, price, height)` with its **consensus key** (Ed25519, domain-separated, bound to the chain id); `price` is an integer with the pair's decimals, `height` the height the validator had executed. Observations are gossiped to the validators (frame kind 5) and the block proposer puts the ones it holds into its payload (the oracle side-channel; at most 1024 per block).
3. The executor verifies each observation in `end_block`, **skipping** (never failing the block) any that is badly signed, from a non-validator of the current epoch, for an unknown pair, from the future or older than `max_age_blocks`, or not strictly newer than that validator's previous one for the pair (a validator cannot go back in time or change its first statement of a height). Accepted ones replace the validator's latest observation.
4. For every pair that got news, the chain takes the **stake-weighted median** (lower weighted median: the first price at which the cumulative stake reaches half of the reporting stake) over the current epoch's validators' fresh observations, **provided at least two thirds of the total stake reported**. Otherwise the previous price stays, and its height tells consumers how stale it is.
5. The result (the *candidate*) is published, held back or paused according to the [update rule and circuit breaker](#update-rule-circuit-breaker-and-twap-built) below. A published price is stored at `price(pair) = {price, height of the update, decimals, number of reporters}` in the state.

**Why a minority cannot move it.** If less than one third of the stake is faulty and at least two thirds of the stake reports, the faulty reporters hold less than half of the reporting weight, so the weighted median is a value reported by an honest validator or lies between two of them; it never leaves the range the honest validators saw (`weighted_median_is_robust_to_less_than_a_third_of_the_stake` checks this on thousands of random stake and report patterns, `a_minority_of_stake_cannot_move_the_price_outside_the_honest_range` on the chain, and a 4-node cluster test with one validator reporting garbage). A Byzantine proposer can omit observations, which only delays an update (a validator's earlier observation remains valid for `max_age_blocks`); it cannot forge or alter one.

Transactions in a block see the prices of the **previous** block (observations are folded in after the transactions), so a transaction cannot depend on an observation in its own block.

**Reading it.**

```rust
#[btb::query]
pub fn btc_price() -> Option<u128> {
    price(0).map(|p| p.price) // free in a query
}

#[btb::mutation]
pub fn liquidate(position: u64) {
    let Some(p) = price(1) else { abort("no price") };
    if p.age_blocks(block_height()) > 5 {
        abort("price too old"); // the contract states how old a price it accepts
    }
    // ...
}
```

- Host call `price(pair, out_ptr)` returns `price: u128`, `height: u64` (update height), `decimals: u8`; `NOT_FOUND` for an unknown pair or no price yet, and **`PRICE_PAUSED` (1) while the feed's circuit breaker is open** (nothing is written to `out_ptr`; contracts that move money on prices must handle it). Old contracts that test `r != 0` simply see "no price". The Rust SDK keeps `price(pair) -> Option<Price>` (paused counts as `None`) and adds `price_checked(pair) -> Result<Price, PriceError>` with `NotFound | Paused`.
- **Fees (reconciled).** A **mutation or cron pays a per-read fee**: the call costs `HOST_PRICE_MUTATION = 200 + 10,000` gas, which like all gas goes to the validator pool and so to the validators that observed and signed prices; the 10,000 is the fee part. A **query pays nothing**: the call costs `HOST_PRICE_QUERY = 200` gas and queries are not billed. `price_twap` follows the same rule: `HOST_TWAP_QUERY = 500` (free to the caller in a query), `HOST_TWAP_MUTATION = 500 + 20,000` in a mutation or cron (two checkpoint reads plus the per-read fee).
- RPC: `btb_oracleConfig`, `btb_oracleDkg`, `btb_oraclePrice [pair]` (with `paused`), `btb_oracleTwap [pair, window]`, `btb_oracleBeacon [height]` ([NODE.md](NODE.md)).

### Sources on the validator (built)

A validator reports a pair only when it has **fresh, agreeing sources**. Config (`price_sources` in `node.json`, see [NODE.md](NODE.md#config-nodejson)), per pair:

```json
{"pair": "BTC/USD", "min_sources": 3, "max_age_ms": 20000, "outlier_bps": 150,
 "sources": [
   {"preset": "binance-example",  "symbol": "BTCUSDT"},
   {"preset": "coinbase-example", "symbol": "BTC-USD"},
   {"name": "my-feed", "url": "https://prices.example.org/btc", "pointer": "/quote/usd", "div": 100}
 ]}
```

- **Adapters.** A source is `url + JSON pointer + scaling`. The pointer (RFC 6901, array indexes allowed: `/data/0/last`) names a JSON string or number. It is parsed from its decimal text (`"64123.45"`, `6.5e4`) into an integer with the pair's decimals, **rounding half up, without floats**, then `* mul / div` (for endpoints that report cents, thousands or another unit). Zero, negative, non-numeric, overflowing and unparsable answers are rejected, as is any non-2xx status.
- **Presets are examples.** `binance-example`, `coinbase-example`, `bitstamp-example` and `okx-example` fill in a public ticker URL and pointer for a market `symbol`. They are marked as examples on purpose: those endpoints belong to third parties, change, have terms of use and regional limits. Check them before relying on one, or write the generic form.
- **Same client as actions.** Sources are fetched with `crate::actions::fetch` under the node's `fetch_policy`: https only, public addresses only (checked on the addresses the connection really uses, so DNS rebinding cannot help), redirects only within the source's own host, response size (`max_bytes`, default 64 KiB, at most 1 MiB) and time (`timeout_ms`, default 3 s, at most 30 s) capped.
- **Never blocks the node.** A background thread refetches every source each `price_fetch_interval_ms` (default 2000), sources in parallel, and keeps the **last good value of each source with its timestamp**. The driver only reads that table when it is time to sign; a slow or dead exchange costs nothing but its own freshness.
- **Staleness, outliers, quorum.** Values older than `max_age_ms` are dropped; at least `min_sources` must remain; the median of the rest is taken; values further than `outlier_bps` from that median are dropped; at least `min_sources` must survive; the median of the survivors is the observation. Otherwise the validator reports nothing for the pair and the chain keeps its previous price (its height shows the age). Use three or more sources: with two, a single liar makes both disagree and the validator stays silent (safe, but silent).
- The validator's observation is therefore a median of sources, and the chain takes the stake-weighted median of those: **a median of medians**. A validator whose sources all lie is a minority fault, covered by the argument above (`validators_fetch_exchange_sources_and_lying_sources_cannot_move_the_price` runs it on four nodes against local mock exchanges).

### Update rule, circuit breaker and TWAP (built)

Genesis `oracle.rules` (all feeds; defaults keep the old behaviour: publish on every block with news, no breaker, TWAP depth 1024):

| Field | Meaning |
| --- | --- |
| `update_deviation_bps` (X) | publish the new aggregate if it differs from the published price by more than X basis points (0: any news) |
| `heartbeat_blocks` (H) | ... or if H blocks passed since the last publication (at least 1) |
| `breaker_bps` (Y), `breaker_window` (Z, at most 256), `breaker_resume_blocks` (K) | circuit breaker; `breaker_bps = 0` turns it off |
| `twap_max_window` | how far back `price_twap` can reach (0 to 10,000; 0 turns TWAPs off) |

Each block with news produces a **candidate** (the stake-weighted median, as before). The sequence in `end_block`:

1. **Breaker.** The chain remembers the candidates of the last Z blocks. If the new candidate is more than Y bps away from any of them, the feed is **paused**: the stored price stays at its last good value, `price` and `price_twap` return `PRICE_PAUSED`, and nothing is published.
2. **While paused**, every block with news is compared with the previous candidate and with the first candidate of the current run. After **K consecutive in-band blocks** (within Y bps of both) the feed **resumes automatically**: the latest candidate is published and becomes the new baseline. A candidate outside the band restarts the count, and a price that drifts away slowly never counts as stable. There is no governance switch: a feed that never settles stays paused, and consumers see that rather than a wrong price. Blocks without news neither count nor reset.
3. **Update rule.** Otherwise the candidate is published if there is no price yet, or it deviates by more than X bps, or H blocks passed since the last publication. The price's `height` is the height of the last publication, so with a deviation rule consumers bound staleness by H (and by their own `age_blocks` check).

**TWAP.** Each publication writes a checkpoint `(height, cumulative, price)` (`50 12 pair height`), where `cumulative` is the sum of `price * blocks`. A price published at block `h` is in force from block `h + 1` (transactions see the previous block's price). `price_twap(pair, window, out_ptr)` returns `(cum(now) - cum(now - window)) / window` with `now` the executing block height; integer math only, wrapping 128-bit sums that are exact while `price * window < 2^128`, floor division, the same bytes on every node. Checkpoints older than `twap_max_window` are pruned (one anchor is kept), and a window longer than the history is refused with `PRICE_BAD_WINDOW` rather than guessed. Output: `twap: u128 LE`, `window: u32 LE`, `decimals: u8`, 11 zero bytes. Status: `0` ok, `NOT_FOUND`, `PRICE_PAUSED` (1), `PRICE_BAD_WINDOW` (2). While a feed is paused its TWAP is paused too.

```rust
#[btb::mutation]
pub fn borrow(amount: u128) {
    match price_checked(0) {
        Ok(p) if p.age_blocks(block_height()) <= 20 => { /* ... */ }
        Err(PriceError::Paused) => abort("feed paused, try later"),
        _ => abort("no usable price"),
    }
    let twap = price_twap(0, 300).unwrap_or_else(|_| abort("no twap")); // 300-block average
}
```

## 3. Custom web data (HTTPS requests)

Any contract can ask for data that no built-in feed covers, such as a sports score, the weather, or an API response. Every validator makes the request itself, a **transform** strips what differs between their responses, and when validators holding at least two thirds of the stake signed the same bytes the chain hands them to the contract in a later block.

```rust
use btb_sdk::oracle::action::{self, HttpRequest, HttpResponse};

// Phase 1: which request should every validator make? Runs read-only, in the requesting transaction.
#[btb::action]
pub fn weather(city: String) -> HttpRequest {
    HttpRequest::get(format!("https://api.example.com/w/{city}")).limits(4096, 3000)
}

// Phase 2 (per validator, off-chain, pure): keep only the stable part of the response.
// The result the validators sign is the canonical encoding of the return value.
#[btb::transform("weather")]
pub fn weather_transform(resp: HttpResponse) -> i32 {
    if resp.status != 200 { btb_sdk::host::abort("upstream not ok") }
    parse_celsius(&resp.body)
}

// Phase 3: the chain delivers the agreed result, in a mutation, in a later block.
#[btb::mutation]
pub fn weather_callback(id: Address, args: Vec<u8>, status: u8, data: Vec<u8>) {
    action::require_callback();               // only the chain may call this
    if status == action::STATUS_OK {
        let celsius = i32::decode(&data).unwrap();
        /* store it */
    }
}
```

A project with the example contract: [`examples/actions`](../examples/actions).

### Lifecycle

1. **Request.** A user sends an `Action` transaction (tag 13, `ActionOp::Request {contract, function, args, gas_limit, max_fee}`). The chain checks that the contract has `btb_action_<function>` **and** a mutation `<function>_callback`, runs the action's first phase read-only (a write traps, so a query-like function cannot change state), decodes the `HttpRequest` it returns and validates it ([below](#what-the-chain-checks)). It escrows `max_fee` from the sender into the actions escrow account and stores a **pending request** with the transaction's id as request id. The receipt's output is that id. At most 256 requests wait at once and at most 16 per account.
2. **Fetch.** Each validator sees the pending request in the state of the block that created it and starts a worker (never on the driver thread): it makes the request under the [SSRF rules](#ssrf-protections), runs `btb_transform_<function>` in a VM with no state access, caps the result at 1 KiB, and signs `(request id, status, data)` with its consensus key (`ActionVote`). Failures are signed too, as `status = 1` with one of a few fixed texts (`blocked`, `timeout`, `fetch failed`, `response too large`, `transform failed`, `http status N`, `result too large`), so that validators who hit the same problem agree on it.
3. **Votes into a block.** Votes are gossiped (oracle frame, tag 20); the proposer adds the ones the chain has not recorded yet to its block payload (`Batch.actions`, at most 512 per block, nothing to do with the price observations).
4. **Verdict, in the same block.** After the transactions and crons, `run_actions` verifies every vote (strict Ed25519 by a validator of the current epoch, over `SHA256("btb.action.vote.v1" || chain_id || request id || status || SHA256(data))`; a bad vote is skipped, never an error), records the first vote of each validator, and for each pending request decides:

| Verdict | When | Callback gets |
| --- | --- | --- |
| Agreed | validators with `>= 2/3` of the epoch's stake signed the **same** `(status, data)` | `STATUS_OK (0)` with the data, or `STATUS_FAILED (1)` with the text, if that is what two thirds agree on |
| Disagreement | even if every validator that has not voted joined the leading outcome, it would stay below `2/3` | `STATUS_DISAGREEMENT (2)`, no data |
| Timeout | the deadline (`created + 50` blocks) passed without agreement | `STATUS_TIMEOUT (3)`, no data |

   The callback is `<function>_callback(request id: Address, args: Vec<u8>, status: u8, data: Vec<u8>)`; `args` are the arguments of the request transaction, returned so the contract needs no bookkeeping. It runs in the same block as a system transaction with caller `actions::CALLER` and a receipt with `Origin::Action`. Deliveries share the cron caps (`max_crons_per_block`, `cron_gas_block_cap`); the ones that do not fit wait for the next block.
5. **Settlement.** The callback's gas (at most `cron_gas_limit`) goes to the validator pool; each validator that **voted** (agreeing or not: it did the work) earns `RESPONSE_GAS = 100,000` gas times the gas price, from what is left of the escrow; the rest is refunded to the requester. The escrow must cover the callback's gas limit plus one answer from every validator of the epoch (`EscrowTooLow` otherwise). Nobody answered: nobody is paid, everything but the callback's gas comes back.

The request is then gone, with its votes. Replaying a vote after that finds no request.

### Transform semantics

* `#[btb::transform("name")]` exports `btb_transform_<name>`; the string names the action (default: the Rust function name, which then must not clash with the action's). It takes the `HttpResponse {status, body}` and returns any encodable value; **the signed bytes are the canonical encoding of that value** ([ENCODING.md](ENCODING.md)), and the callback decodes `data` as the same type.
* It is **pure**: it runs with a host that has no storage, tables, balances, prices or randomness, every state-changing call traps, and the clock does not exist. Same response in, same bytes out.
* It is metered: `FetchPolicy::transform_gas` (default 20M); running out of gas or trapping becomes the agreed failure `transform failed`.
* **No transform:** the signed result is the raw body of a 2xx response (any other status is the failure `http status N`). Validators that see different bytes then disagree, which is the right outcome for data that is not stable (the tests show both).
* Agreement is **byte exact**. For numbers that legitimately differ slightly between validators (a price moving between two fetches) the transform should round or bucket, or the contract can ask several times; a median over validators' own readings is how the built-in price feeds work ([section 2](#2-price-feeds-and-real-time-data)).

### What the chain checks

At request time, before anything is fetched (all of it from the state every validator has, so every validator reaches the same verdict):

* **Host allowlist, per contract.** The contract's **deployer** sets it with `ActionOp::SetHosts` (tag 13, sub 1): entries are `host` (any port), `host:port` or `*.suffix` (a subdomain, never the bare suffix; `*.com` is refused). With no list nothing may be called. A request keeps the list it was made with, so changing it does not change what is in flight.
* **URL.** `http://` or `https://`, printable ASCII, no user info, no IPv6 literal, a DNS name or a clean dotted IPv4 (hex, octal and integer forms are refused), valid port. The host (and port) must match the allowlist.
* **Headers and body.** At most 16 headers (name `[A-Za-z0-9_-]`, printable value, name plus value at most 512 bytes), none of `Host`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Upgrade`, `TE`, `Proxy-*`; a body of at most 4 KiB, only on POST.
* **Limits.** `max_response_bytes` (default 16 KiB, at most 1 MiB) and `timeout_ms` (default 5 s, at most 10 s); more is refused rather than silently clamped.
* **Callbacks are system only.** A transaction that calls `<action>_callback` is refused (`CallbackIsSystemOnly`), whoever sends it. `action::require_callback()` is a second lock inside the contract.

### SSRF protections

A validator is asked by anyone to fetch URLs, so it protects itself (`btb-node/src/actions.rs`, `FetchPolicy`; the defaults are the strict ones):

* only `https`, unless `allow_http` (tests);
* only **public addresses**: loopback, private (`10/8`, `172.16/12`, `192.168/16`), link-local (including the `169.254.169.254` cloud metadata address), carrier-grade NAT, documentation and benchmarking ranges, multicast, reserved, IPv6 unique-local, link-local and site-local, IPv4-mapped and NAT64 forms of those, 6to4 and Teredo, are refused unless `allow_private` (tests). The check runs inside the HTTP client's **resolver**, on the addresses the connection will use, so a name that resolves to a private address, or to a public address at check time and a private one at connect time (DNS rebinding), cannot get through;
* **redirects** are followed by hand (the client follows none): at most 3, and every target must pass the same URL, allowlist and scheme checks, so a public allowlisted host cannot bounce a validator to an internal one. `301`, `302` and `303` turn a POST into a GET;
* the request's own time limit covers the whole exchange including redirects and reading the body; the body is read at most `max_response_bytes + 1` bytes.

The HTTP client is `ureq` (MIT OR Apache-2.0, blocking, rustls with the `ring` provider and the `webpki-roots` trust anchors) behind the `https` feature of `btb-node` (on by default). Without it every fetch fails with `fetch failed`, identically on every such node, and the chain still works.

### Why it is safe

* **Only validators speak.** A vote needs a valid signature by a validator key of the current epoch, bound to chain id and request id: it cannot be replayed on another chain or request, a request's votes die with it, a second vote by the same validator is ignored (first wins), and non-validators, operators' account keys, wrong statuses and oversized results are skipped.
* **Agreement is stake weighted and byte exact.** `2/3` of the stake behind identical bytes; with less than a third of the stake faulty that result is one an honest validator computed from its own fetch.
* **A proposer cannot force or hide a result.** It can only omit votes (delaying at worst to the deadline, after which the contract still gets an answer) or include genuine ones.
* **Everything ends.** Each request is settled within `DEADLINE_BLOCKS` (50), the queue is bounded, so state and work are bounded.
* **Queries cannot start actions.** There is no host call that creates a request; only an `Action` transaction does. An action is not a query (`NoSuchFunction`), and a `Call` transaction must be a mutation (`KindNotAllowed` for query and action kinds).
* **Determinism** of the chain side is the executor's: votes enter through the block, the verdict is a function of state, and sequential and parallel execution agree (tested).

### Who pays

The requester, in advance: the transaction's gas, plus the escrow (`max_fee`) that pays the validators' answers and the callback (as above). **Validators doing the work are paid.** It scales with the number of validators on purpose: the contract pays for every validator's request, so expensive or frequent calls cost accordingly.

### Limits

* The source must give consistent answers to all validators within a short window. APIs that require secret keys need extra care: a key given to all validators is visible to all of them (put per-request secrets in a proxy you control, or use a key that is meant to be public).
* A contract that stores data in its callback must hold enough balance for the storage deposit (the callback fails with a deposit fault otherwise, and the result is lost: the request is already settled).
* Results are at most 1 KiB; for bulk data, return a hash and fetch the data elsewhere.
* Followers (non-validators) answer nothing; only validators of the epoch are counted.

## 4. BTB as an oracle for other chains

Because BTB validators hold the threshold key of the [randomness beacon](#1-verifiable-randomness) (the same BLS12-381 committee key), BTB can **serve its prices and any other data to other chains**:

1. A contract queues a **report** (bytes, at most 1 KiB) with the `report_request` host call (call 42; `btb_sdk::oracle::report::request`). Mutations and crons only: a query, an action or a transform traps like any other state change. The runtime stores it under `52 01 id` with the height and the asking contract, and returns the id (a chain-wide counter).
2. The committee signs `"btb.report.v1" || chain_id:u64be || contract[32] || id:u64be || SHA256(data)` with the group key of the epoch the report was queued in. Each holder releases a partial (frame tag 21), anyone combines `threshold` valid partials into **the** group signature (BLS signatures are unique, so every node ends with the same 96 bytes), and a node that missed partials asks (`ReportWant`) and checks what it gets. The signature binds the chain, the contract and the id, so a report cannot be replayed for another contract or chain, and its message prefix differs from the beacon's, so it can never be mistaken for a beacon value.
3. A relayer fetches it over RPC, `btb_oracleReport [id]` (`{id, chain_id, contract, height, epoch, data, message, group_key, signature}`; `signature` is `null` until it is ready, the whole result `null` for an unknown or pruned id), and submits it to the target chain.
4. A small verifier on that chain checks the single signature against the committee's 48-byte group key and uses the value.

Reports stay in chain state for 100,000 blocks (`btb_chain::reports::RETENTION_BLOCKS`); the signature is kept in memory by every validator and re-derived after a restart. Per call at most 8 reports; the host call costs `5,000 + 10 * len` gas, which goes to the validators like all gas.

### Verifier (Rust)

```rust
use btb_oracle::report::verify;

/// `group_key`: the committee's 48-byte compressed BLS12-381 public key (from `btb_oracleConfig`
/// or the `group_key` field of the report), pinned by the verifier.
fn accept(group_key: &[u8; 48], chain_id: u64, contract: &[u8; 32], id: u64,
          data: &[u8], signature: &[u8; 96]) -> bool {
    verify(group_key, chain_id, contract, id, data, signature)
}
```

`verify` is total: malformed keys and signatures, points outside the subgroup and the identity all return `false`. It checks `e(pk, H(msg)) == e(g1, sig)` with `H` the RFC 9380 `BLS12381G2_XMD:SHA-256_SSWU_RO_` hash-to-curve and the domain separation tag `BTB_BEACON_BLS12381G2_XMD:SHA-256_SSWU_RO_V1_` (the beacon's; the message prefix keeps the two apart).

### Verifier (Solidity sketch)

> A sketch, not compiled and not audited. It needs an EVM chain with the BLS12-381 precompiles of [EIP-2537](https://eips.ethereum.org/EIPS/eip-2537) (Ethereum since the Prague/Electra upgrade). The relayer decompresses the 96-byte signature to EIP-2537's 256-byte encoding (and the key, once, at deployment, to its 128-byte encoding) off-chain.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract BtbReportVerifier {
    address constant G2ADD      = address(0x0d);
    address constant PAIRING    = address(0x0f);
    address constant MAP_FP2_G2 = address(0x11);

    bytes public groupKey;         // 128 bytes: the committee key, EIP-2537 G1 encoding
    bytes public negG1Generator;   // 128 bytes: -g1, EIP-2537 G1 encoding
    uint64 public immutable btbChainId;
    mapping(bytes32 => bool) public used;

    constructor(bytes memory _groupKey, bytes memory _negG1, uint64 _btbChainId) {
        groupKey = _groupKey; negG1Generator = _negG1; btbChainId = _btbChainId;
    }

    /// What the committee signed (all integers big endian, as on BTB).
    function message(bytes32 btbContract, uint64 id, bytes calldata data)
        public view returns (bytes memory)
    {
        return abi.encodePacked("btb.report.v1", btbChainId, btbContract, id, sha256(data));
    }

    /// Accept `data` as report `id` of `btbContract` if the committee signed it.
    function submit(bytes32 btbContract, uint64 id, bytes calldata data, bytes calldata sig256)
        external returns (bool)
    {
        bytes32 key = keccak256(abi.encode(btbContract, id));
        require(!used[key], "replay");                  // each report once
        require(sig256.length == 256, "bad signature");
        bytes memory h = hashToG2(message(btbContract, id, data));
        // e(pk, H(m)) * e(-g1, sig) == 1
        (bool ok, bytes memory out) = PAIRING.staticcall(
            abi.encodePacked(groupKey, h, negG1Generator, sig256));
        require(ok && out.length == 32 && abi.decode(out, (uint256)) == 1, "invalid signature");
        used[key] = true;
        /* use `data` */
        return true;
    }

    /// RFC 9380 hash_to_curve for BLS12381G2_XMD:SHA-256_SSWU_RO_ with the DST of the beacon:
    /// expand_message_xmd(SHA-256, msg, DST, 256) into two Fp2 elements, map each with the
    /// MAP_FP2_TO_G2 precompile, add the two points with G2ADD (clearing the cofactor is part
    /// of the precompile's map). `expand_message_xmd` takes a dozen lines of SHA-256 calls.
    function hashToG2(bytes memory msg_) internal view returns (bytes memory) { /* ... */ }
}
```

A chain without the BLS precompiles (or Solana, where the cost matters) needs a different check; the planned **threshold-ECDSA variant** signs the same message with the cross-chain key of [CROSS_CHAIN.md](CROSS_CHAIN.md) so that an `ecrecover` against a pinned address is the whole verifier. That key does not exist yet, which is why only BLS reports are built.

Tests: `crates/btb-oracle/src/report.rs` (the message), `crates/btb-vm/tests/actions.rs` (the host call: gas, limits, read-only), `crates/btb-runtime/tests/reports.rs` (ids, records, gates), `crates/btb-chain/src/reports.rs` (listing and pruning), `crates/btb-node/tests/reports_cluster.rs` (four real nodes: the signature verifies with nothing but the group key, fails for any other contract, id, chain, data or committee, and still appears with a validator down).

## Economics

Oracle work is paid like everything else on BTB: **whoever does the work gets paid.**

| Service | Who pays | Who earns |
| --- | --- | --- |
| Randomness | Mutation's gas (`300 + 2 * len` per call, and the full gas limit is charged) | Validators |
| Built-in price feeds | Apps that read them **in mutations and crons**, through a per-read fee (10,000 gas on top of the 200 gas read); **queries pay nothing** | Validators that observe and sign prices (through the validator pool) |
| App-defined feeds | The app that created the feed, from its prepaid balance | Validators |
| Custom HTTPS requests | The requester, in advance: the transaction's gas plus an escrow (callback gas limit + `100,000` gas per validator); the unused part is refunded | Each validator that answered earns `100,000` gas; the callback's gas goes to the validator pool |
| Reports for other chains | The mutation or cron that queues it (`5,000 + 10 * len` gas, like all gas) | Validators |

## Risks and limits

| Risk | Mitigation |
| --- | --- |
| Validators collude to fake a price | Same trust as the chain itself: requires two-thirds collusion. Stake-weighted median over at least two thirds of the stake tolerates less than a third of faulty stake. |
| The beacon key was dealt by one party | Gone by default: the validators generate the key on chain. Only `--insecure-dealer` (testnets) has a dealer. |
| The beacon committee must follow the validator set | It does: resharing at every epoch change. If a resharing fails (too many silent/cheating dealers) the old key and holders carry over while at least a threshold of them are still validators; if not, the chain enters degraded mode (no beacon, `RandomnessUnavailable`) and runs a fresh DKG, which changes the group key (see Losing the beacon committee). |
| A block waits for its beacon | One extra round trip per block; a missing beacon stalls execution (never produces a wrong one). Peers answer `Want` with verified values. |
| Sources are manipulated (thin markets, a single exchange) | Many independent sources, volume-weighted medians, circuit breakers, TWAPs |
| Stale data during network issues | Every value carries its age; contracts must declare a maximum age |
| One feed's failure halts apps | Feeds pause safely; apps can define fallbacks (another feed or a TWAP) |
| Data licensing and API terms | Built-in feeds use sources whose terms allow this use; app-defined feeds are the app's responsibility |
| Validator load from many feeds and requests | Feeds and requests are paid per use; at most 256 pending actions (16 per account), 512 votes per block, callbacks under the cron gas caps; reports capped per call and pruned |
| A contract makes validators call an internal service (SSRF) | Per-contract host allowlist, public addresses only (checked at connect time), https only, redirects re-checked, size and time caps ([section 3](#ssrf-protections)) |
| A response differs between validators | The transform strips what varies; without agreement the contract gets `STATUS_DISAGREEMENT` instead of a wrong value, and a deadline guarantees an answer |
| A user feeds a contract a made-up result | The callback runs only from the chain's own delivery (system caller, direct calls refused) |

## Rollout

Oracles are part of **Phase 5** in the [roadmap](../ROADMAP.md):

1. On-chain randomness (threshold BLS beacon): **built**, with on-chain DKG and per-epoch resharing (no trusted dealer; stake-weighted virtual shares open)
2. Built-in price feeds: **built**, with real exchange sources on the validator (background fetch, same SSRF-safe client as actions), a deviation/heartbeat update rule, a circuit breaker and TWAPs; publishing source count and spread is open
3. Custom HTTPS requests with transforms: **built** (see section 3)
4. Signed reports for other chains: **built for BLS verifiers** (EVM via EIP-2537; the threshold-ECDSA variant waits for the cross-chain key)

See [Prior art](PRIOR_ART.md#chainlink-and-randomness-beacons) for how Chainlink, the Internet Computer, Aptos and drand approach the same problems.
