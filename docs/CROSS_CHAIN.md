# Cross-Chain Design

BTB contracts can read from and write to other chains — Ethereum, Bitcoin, Solana and more — **without deploying contracts there**. The logic always runs on BTB; other chains only see ordinary transactions.

## Writing: chain signatures

BTB validators jointly hold keys using threshold cryptography (MPC). No single validator ever has a full key, but when two-thirds agree they produce a valid signature together. Those keys control normal addresses on other chains:

- An Ethereum address, a Bitcoin address, a Solana account — each owned by a BTB contract.
- A contract calls something like `eth.send_tx(...)`; validators sign it; it lands on Ethereum as a normal transaction.
- The target chain does not know BTB exists, so nothing is deployed there.

Supported signature schemes: Schnorr over secp256k1 (Bitcoin Taproot, **built**), EdDSA (Solana, **built**), threshold ECDSA (Ethereum, Bitcoin legacy, **not built**, see [Ethereum](#ethereum-threshold-ecdsa-is-not-built-yet)).

NEAR (Chain Signatures) and the Internet Computer (Chain Fusion) already run this approach in production.

## Keys

One FROST key per scheme, generated by the validators of epoch 0 and **reshared at every epoch change** with the same transport as the beacon DKG ([ORACLES.md](ORACLES.md#key-provisioning-and-the-dkg)): every dealer posts Feldman commitments plus one encrypted share per recipient (`CrossOp::Deal`, transaction tag 21), a recipient with a wrong share posts a decryption proof (`Complain`) and the chain decides it itself. A cross-chain session opens in the same block as the beacon session it mirrors, with the same committee and window. The threshold is above two thirds (`t = n - floor((n-1)/3)`). A failed generation keeps the previous key and its holders.

* The group key is the DKG output. For Taproot that is the **internal key** `P`; the address commits to the BIP-341 output key `Q = lift_x(P) + H_TapTweak(P)G` (key-path spend, no script tree), and signatures verify under `Q` with any BIP-340 verifier. Deposit addresses: `bc1p...` (bech32m) for Bitcoin, base58 for Solana (`btb_crossKeys`).
* Resharing: each old holder deals its own share (its constant commitment must equal its published public share), the new committee combines with Lagrange weights. The secret is never reconstructed and the group key is unchanged.
* No proof of knowledge of the constant term is needed (a dealer that does not know the discrete log of its commitment cannot make shares that verify and is disqualified). As with any joint-Feldman DKG a rushing adversary can bias the distribution of the group key, which does not help forging signatures.
* Old shares stay valid for the same key after a reshare. Honest holders delete shares (and nonces) of older generations once a newer key is in use; a coalition of `t` *old* holders that kept their shares could still sign, which is why the threshold is above two thirds and why vault value must stay below what slashable stake covers.

## Signing

A native module queues a request (32-byte message, scheme) with `xsign::request`; there is no transaction for it, so no account can ask for a signature over an arbitrary message. Validators then run numbered attempts:

1. The signer set of attempt `a` is a pure function of chain state: the `t` holders with the smallest `H(key, request, a, holder)` among those not excluded.
2. **Round 1, preprocessed.** Holders keep a pool of nonce pairs and publish commitments in batches (`XMsg::Pool`). A signer announces which commitment it uses with a signed `Use`.
3. **Round 2.** All build the same package (message from chain state, commitments from the pools). Each signer takes its nonce out of its pool, **persists the pool, then** computes and gossips a signed share. Any node aggregates; one signature results, nodes submit it on chain (`CrossOp::Signature`, staggered by hash rank) where it is verified with the verifier an external chain uses, stored, and served by `btb_crossRequest`.
4. **Robustness.** A timed-out attempt is replaced by attempt `a + 1` (another signer set). A share that fails verification identifies its signer (FROST cheater detection); the node files evidence and retries without them.

**Nonce reuse is prevented** by construction: nonces come from OS randomness (never from the share), `NonceStore::take` removes a nonce and syncs the file before the share exists, and the announcement per `(request, attempt)` is persisted so a restarted node repeats it. A crash loses a nonce; nothing can reuse one. A node with no data directory keeps this in memory and must not be restarted while it has requests in flight.

**Evidence** (`CrossOp::Evidence`, checkable by anyone): a share that does not verify for the package the signer itself signed, or two different signed announcements for one attempt. Recording it excludes the signer from signer sets of the current and next epoch. State: `70 30`.

## Vault and wrapped tokens

`btb-chain::vault`, one vault per scheme (Bitcoin: Taproot, Solana: Ed25519).

* **Wrapped assets are user tokens, never BTB.** They live in the native token ledger with the vault as sole mint authority (`wBTC`, 8 decimals; `wSOL`, 9). The fixed BTB supply is untouched; the vault code never reads or writes a BTB balance (every block still checks the supply invariant).
* **Minted only against observed deposits.** Validators vote (`Attest`) for a deposit claim (`txid`, index, amount, recipient named in the deposit memo). A claim is credited once, when voters hold at least two thirds of the epoch's stake for the *identical* claim. Invariant tested: `supply == credited - burned`, and credited equals the quorum-confirmed deposits.
* **Withdrawals burn before they sign.** `Withdraw` burns at once. Validators vote (`Prepare`) for the unsigned external transaction (digest and sighashes); at two thirds, one signing request per sighash is queued. A withdrawal is prepared at most once, so one burn cannot yield two signed transactions.
* The observer is an interface (`vault::Observer`); the mock is the only implementation. The memo format for the recipient (Bitcoin `OP_RETURN`, Solana memo) is part of the planned watchers.

## Threat model

| Threat | Mitigation | Remaining |
| --- | --- | --- |
| A signer submits a bad share | identified, evidence, excluded, retry | no slashing yet |
| Nonce reuse leaking a share | single-use persisted nonces | disk failure that rolls back the file |
| Fewer than `t` colluding holders | information-theoretic | none |
| `t` or more validators collude | can sign anything for every vault | vault caps; stake must exceed vault value |
| Validators lie about a deposit | two thirds of stake must agree | same collusion bound; real watchers, light clients planned |
| Prepared transaction does not match the burn | two-thirds agreement only | chain-side parsing planned |
| Withdrawal burned but never executable | none yet | refunds planned |
| Reshare fails and fewer than `t` old holders remain validators | key is stuck (funds frozen) | churn limits, caps; degraded-mode recovery of the beacon does not apply to vault keys |
| A validator floods fake claims | each costs fees | per-validator claim quota planned |

## Ethereum: threshold ECDSA is not built yet

Ethereum needs secp256k1 ECDSA, which has no cheap threshold form. Options, none implemented: CGGMP21 (Paillier-based, malicious security with identifiable abort, heavy setup and presigning), DKLs23 (OT-based, two-round signing, no Paillier), or Lindell-style two-party schemes with a validator-run co-signer. The choice needs an audit budget and a decision on resharing, which these protocols make harder than FROST.

**Interim path:** the committee's BLS signature on a report ([ORACLES.md](ORACLES.md#4-btb-as-an-oracle-for-other-chains)) verified on Ethereum by a contract using the EIP-2537 precompiles (Solidity sketch there). A BTB-controlled Ethereum *address* (an EOA that sends transactions) is not possible without ECDSA; a contract wallet that accepts BLS-signed instructions is the stand-in.

## Reading: validator-agreed observations

Users never supply RPC endpoints, because a single RPC can lie. Validators each observe other chains through their own nodes or several providers and agree on the result in consensus. Later, light clients that verify the other chain's proofs directly can replace trust in RPC data.

## Example: native cross-chain swap

1. A user sends real ETH to a BTB-controlled Ethereum vault address.
2. Validators observe the deposit and credit the user inside the BTB DEX.
3. The user swaps ETH for SOL on BTB — instant and cheap.
4. BTB signs a Solana transaction sending real SOL from its Solana vault to the user's wallet.

No wrapped tokens and no bridge contracts. A BTB contract can also call existing contracts on other chains, for example executing a swap on Uniswap from a BTB-owned Ethereum address.

## Limits and risks

| Limit | Implication |
| --- | --- |
| No custom logic on other chains | If logic must run inside Ethereum atomically with other Ethereum contracts, a contract is still needed there |
| Gas on each target chain | Vault addresses need ETH, SOL, etc. for fees; the protocol charges users and keeps vaults topped up |
| Speed of the slowest chain | Bitcoin deposits need several confirmations; Ethereum needs minutes for safe finality |
| Validator collusion | Two-thirds of validators control every vault. Vault value must stay below what slashable BTB stake covers — the classic bridge risk |
| Liquidity in vaults | Real assets must sit in each chain's vault for withdrawals to work |
